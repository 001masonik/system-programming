## 1. Що таке система контролю версій (VCS)

**Система контролю версій (Version Control System, VCS)** — це програмне забезпечення для полегшення роботи зі змінною інформацією. Вона фіксує всі зміни у файлах проекту з плином часу, дозволяючи:
- Переглядати повну історію проекту;
- Повертатися до будь-якої попередньої версії файлів чи проекту в цілому;
- Відстежувати, хто саме, коли і які зміни вніс;
- Безпечно працювати над спільним кодом у команді без ризику перезаписати чужі напрацювання.

### Порівняння систем контролю версій:
| Тип VCS | Приклади | Принцип роботи |
| :--- | :--- | :--- |
| **Централізовані (CVCS)** | SVN, CVS, Perforce | Єдиний центральний сервер, на якому зберігається вся історія. Якщо сервер недоступний — робота команди блокується. |
| **Розподілені (DVCS)** | Git, Mercurial | Кожен розробник клонує на свій комп'ютер повну копію всього репозиторію з усією історією. Робота може тривати повністю автономно (офлайн). |

## 2. Про Git та його архітектуру

**Git** — це найпопулярніша у світі розподілена система контролю версій з відкритим вихідним кодом.
- **Автор:** Лінус Торвальдс (творець ядра Linux);
- **Рік виходу:** 2005;
- **Ліцензія:** GNU General Public License v2;
- **Основні характеристики:** висока швидкість роботи, цілісність даних (криптографічне хешування SHA-1/SHA-256), підтримка нелінійної розробки (тисячі паралельних гілок).

## 3. Три стани файлів у Git

У проекті під керуванням Git файли можуть перебувати в одній із трьох основних зон:

```
[ Робочий каталог ]  ──git add──>  [ Індекс (Staging Area) ]  ──git commit──>  [ Репозиторій (.git) ]
 (Working Directory)                    (Підготовлені файли)                      (Збережена історія)
```

1. **Робочий каталог (Working Directory):** витягнуті з бази даних файли, над якими ви безпосередньо працюєте та редагуєте.
2. **Область індексування (Staging Area / Index):** проміжний шар, де збираються файли та зміни, які увійдуть до наступного коміту.
3. **Репозиторій (Git Directory / Repository):** база даних Git, де зберігаються всі метадані та об'єкти зафіксованої історії.

## 4. 10 основних команд Git

Нижче наведено базовий набір з 10 команд, необхідних для щоденної розробки:

### 1. `git init`
Ініціалізує новий локальний репозиторій Git у поточному каталозі. Створює приховану папку `.git`.
```bash
# Створити новий репозиторій у поточній папці
git init

# Ініціалізувати репозиторій у новому каталозі my-project
git init my-project
```

---

### 2. `git clone`
Клонує існуючий віддалений репозиторій (з GitHub, GitLab тощо) на локальний комп'ютер.
```bash
# Клонувати репозиторій через HTTPS
git clone https://github.com/username/repository.git

# Клонувати в конкретну папку
git clone https://github.com/username/repository.git my-folder
```

---

### 3. `git add`
Додає зміни з робочого каталогу до області підготовки (Staging Area).
```bash
# Додати конкретний файл
git add index.html

# Додати всі змінені та нові файли поточного каталогу
git add .
```

---

### 4. `git commit`
Фіксує підготовлені зміни в репозиторії зі зрозумілим описом виконаної роботи.
```bash
# Зафіксувати зміни з повідомленням
git commit -m "feat: додати розмітку головної сторінки"

# Додати зміни у відстежуваних файлах та створити коміт однією командою
git commit -am "fix: виправити навігаційне меню"
```

---

### 5. `git status`
Відображає поточний стан робочого каталогу та індексу (які файли змінено, підготовлено або не відстежуються).
```bash
# Повний статус
git status

# Короткий компактний статус
git status -s
```

---

### 6. `git diff`
Показує порядкові відмінності між файлами: які рядки додано (`+`), а які видалено (`-`).
```bash
# Різниця між робочим каталогом та індексом
git diff

# Різниця між підготовленими змінами (Staging) та останнім комітом
git diff --staged
```

---

### 7. `git branch`
Керує гілками репозиторію: перегляд, створення, видалення або перейменування.
```bash
# Список локальних гілок
git branch

# Створити нову гілку
git branch feature/login

# Видалити гілку
git branch -d feature/login
```

---

### 8. `git checkout` / `git switch`
Перемикає робочий каталог на іншу гілку або відновлює стан файлів.
```bash
# Перемкнутися на існуючу гілку
git checkout main
# або сучасний аналог:
git switch main

# Створити нову гілку і одразу перейти на неї
git checkout -b feature/dark-theme
# або:
git switch -c feature/dark-theme
```

---

### 9. `git merge`
Зливає зміни із зазначеної гілки в поточну активну гілку.
```bash
# Переконатися, що ви знаходитесь на цільовій гілці
git checkout main

# Злити гілку feature/dark-theme у main
git merge feature/dark-theme
```

---

### 10. `git push`
Надсилає зафіксовані локальні коміти до віддаленого репозиторію на сервері.
```bash
# Надіслати коміти гілки main до віддаленого сховища origin
git push origin main

# Надіслати нову гілку зі встановленням відстеження (upstream)
git push -u origin feature/dark-theme
```

## 5. Типовий робочий процес (Workflow)

```bash
# 1. Створити та перейти на нову гілку для задачі
git switch -c feature/new-page

# 2. Внести зміни у файли проекту та перевірити статус
git status

# 3. Додати зміни до індексу
git add .

# 4. Зафіксувати коміт
git commit -m "feat: додати нову сторінку"

# 5. Опублікувати гілку на віддаленому сервері
git push -u origin feature/new-page

# 6. Після перевірки злити в main
git switch main
git merge feature/new-page
git push origin main
```
